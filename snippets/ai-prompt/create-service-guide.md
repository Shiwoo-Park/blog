# 서비스 온보딩 문서 생성/업데이트

## 변수(프로젝트별로 치환해서 사용)

아래 항목들은 조직/레포/도메인에 따라 달라지는 값들입니다. 문서/프롬프트에서 **코드의 변수처럼** 취급하고, 프로젝트에 맞게 먼저 정한 뒤 나머지 내용을 작성하세요.

- **`ORG_NAME`**: 조직/회사/프로덕트 이름 (예: `Acme`, `OOO팀`)
- **`SERVICE_NAME`**: 온보딩 대상 서비스/도메인 이름 (예: `결제`, `정산`, `주문`)
- **`DOC_ROOT`**: 온보딩 문서 루트 디렉토리 (예: `docs/onboarding`, `docs/services`)
- **`DOC_PATH`**: 대상 문서 경로 패턴 (예: `{DOC_ROOT}/{SERVICE_NAME}.md`)
- **`CODE_ROOT`**: 코드 루트 패턴 (예: `apps`, `src`, `backend`)
- **`APP_NAME`**: (Django 등) 앱 이름/모듈 이름 (예: `orders`, `payment`)
- **`CHANNELS`**: 시스템 채널/클라이언트 구분 (예: `Web`, `Partner`, `Admin` / `B2C`, `B2B`, `Backoffice`)
- **`API_PREFIXES`**: 채널별 URL prefix (예: `/api/v1`, `/partner`, `/admin`)
- **`SAMPLE_DOCS`**: 참고할 “잘 작성된 문서” 목록 (예: `{DOC_ROOT}/_sample.md`, `{DOC_ROOT}/payment.md`)

## 목적

조직/서비스에 대해 아무것도 모르는 **비개발자 또는 신규 개발자**가 서비스 개발을 위해 정책 또는 기존 스펙을 빠르게 파악할 수 있도록, 온보딩 문서를 **생성하거나 업데이트**합니다.

## 사용 방법

## 작업 절차

### 1. 문서 상태 파악

멘션된 문서를 읽고 현재 상태를 확인합니다:

- **빈 문서 또는 간단한 내용만 있는 경우**: 기본 틀을 제공하고 핵심 내용을 채웁니다
- **이미 내용이 충실한 경우**: 문서 구조와 내용을 분석하여 누락/업데이트가 필요한 부분을 찾아 수정합니다

### 2. 관련 코드 스캔

문서에서 언급된 또는 서비스명과 관련된 핵심 모듈을 스캔합니다:

- **모델**: `apps.{app_name}.models*` 또는 문서에 명시된 모델
- **뷰/엔드포인트**: `apps.{app_name}.views*`, `apps.{app_name}.urls*`
- **서비스 로직**: `apps.{app_name}.services*`
- **비즈니스 로직**: Validator, Creator, Repository 등
- **관련 문서**: `docs/onboarding` 하위의 연관 문서들

### 3. 문서 구조 (기본 틀)

아래 구조를 기본으로 하되, 서비스 특성에 맞게 섹션을 추가/수정할 수 있습니다:

### 4. 작성 원칙

#### 대상 독자

- 서비스를 처음 접하는 비개발자 (기획자, PM 등)
- 신규 입사 개발자
- 해당 서비스 도메인을 처음 다루는 기존 개발자

#### 작성 스타일

- **간결하고 명확하게**: 한 문장으로 핵심을 전달
- **구조화된 정보**: 표, 리스트, 섹션 구분을 활용
- **예시 포함**: 이해를 돕는 구체적인 예시 (필요시)
- **용어 정리**: 혼동하기 쉬운 용어는 명확히 구분 (예: 판매처 vs 거래처)
- **시각적 구분**: 표, 코드 블록, 인용문 등을 활용하여 가독성 향상

#### 내용 우선순위

1. **개념 이해**: 서비스가 무엇인지, 왜 필요한지
2. **핵심 정책**: 반드시 알아야 할 비즈니스 룰
3. **모델 구조**: 데이터 구조 이해
4. **API 엔드포인트**: 어떤 기능이 있는지
5. **비즈니스 로직**: 주요 프로세스 흐름
6. **코드 진입점**: 상세 구현을 찾아갈 수 있는 시작점

### 5. 기존 문서 업데이트 시 체크리스트

기존 문서가 충실한 경우, 아래 항목들을 확인하여 누락/업데이트가 필요한 부분을 찾습니다:

#### 모델 정보 검증

- [ ] 문서에 언급된 모델이 실제 코드에 존재하는가?
- [ ] 모델 경로가 정확한가?
- [ ] 중요한 모델이 누락되지 않았는가?
- [ ] 모델의 주요 필드 설명이 정확한가?
- [ ] 모델 간 관계가 명확히 설명되어 있는가?

#### 엔드포인트 정보 검증

- [ ] 문서에 언급된 엔드포인트가 실제로 존재하는가?
- [ ] URL 패턴이 정확한가?
- [ ] HTTP 메서드가 올바른가?
- [ ] 새로 추가된 엔드포인트가 누락되지 않았는가?
- [ ] 엔드포인트 설명이 기능을 명확히 전달하는가?

#### 비즈니스 로직 검증

- [ ] 주요 프로세스가 현재 코드와 일치하는가?
- [ ] 검증 로직이 정확히 설명되어 있는가?
- [ ] 경로별 차이점(웹/파트너/CMS)이 명확한가?
- [ ] 최근 변경된 로직이 반영되어 있는가?

#### 정책 정보 검증

- [ ] 핵심 정책이 모두 포함되어 있는가?
- [ ] 정책 설명이 최신 상태인가?
- [ ] 예외 케이스가 명시되어 있는가?
- [ ] 제약사항이 명확히 설명되어 있는가?

#### 코드 진입점 검증

- [ ] 언급된 클래스/함수가 실제로 존재하는가?
- [ ] 모듈 경로가 정확한가?
- [ ] 주요 진입점이 누락되지 않았는가?

#### 문서 구조 검증

- [ ] 섹션 구성이 논리적인가?
- [ ] 목차가 내용을 잘 반영하는가?
- [ ] 중복된 내용이 없는가?
- [ ] 가독성이 좋은가? (표, 리스트, 구분선 활용)

### 6. 실행

1. 위 체크리스트를 기반으로 코드를 스캔합니다
2. 누락되거나 업데이트가 필요한 부분을 파악합니다
3. 문서를 수정/보완합니다
4. 수정 사항을 요약하여 사용자에게 보고합니다

## 참고 문서

- `{SAMPLE_DOCS[0]}`: 기본 문서 템플릿
- `{SAMPLE_DOCS[1]}`: 잘 작성된 온보딩 문서 예시
- `{SAMPLE_DOCS[2]}`: 복잡한 서비스의 온보딩 문서 예시
- `{SAMPLE_DOCS[3]}`: 외부 연동 서비스 온보딩 문서 예시

## 주의사항

- 레거시 코드를 참고하지 말고 `.cursor/rules/` 의 규칙을 우선 참조
- 코드 구현 세부사항보다는 **개념과 정책** 위주로 작성
- 비개발자도 이해할 수 있는 수준으로 작성
- 불확실한 내용은 추측하지 말고 사용자에게 질문
