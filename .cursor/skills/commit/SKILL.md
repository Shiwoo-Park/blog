# 코드 커밋 & 푸시

이 저장소(GitHub Pages 블로그)의 변경사항을 커밋/푸시할 때 사용한다.
**커밋 메시지는 반드시 사용자 확인을 받은 뒤에만 커밋한다.**

## 작업 순서

1. `git status`, `git diff`(스테이징 전/후 모두), `git log --oneline -5`로 현재 변경사항과 최근 커밋 스타일을 확인
2. 변경사항을 기반으로 간결한 커밋 메시지 작성
3. 변경 종류에 맞는 prefix 부여 (아래 규칙 참고)
4. 작성한 커밋 메시지를 사용자에게 제시하고 확인 요청
5. 보완 요청이 오면 수정해서 다시 확인 요청 (확정될 때까지 반복)
6. "커밋", "진행", "OK", "확인" 등으로 확정되면 그대로 커밋
7. 푸시 요청이 있었거나 확정 메시지에 푸시가 포함되면 `git push`

## Prefix 규칙

| prefix | 사용 기준 |
|--------|-----------|
| `dev`  | 사이트 개발 코드 관련 변경 (레이아웃, 스크립트, 설정, 메타태그 등) |
| `post` | 블로그 포스팅 관련 변경 (`posts/`, `snippets/`, 각 `home.md`) |
| `etc`  | 위 둘 중 어디에도 속하지 않는 변경 (AI 프롬프트, 문서, 잡다한 설정) |

- 한 커밋에 여러 종류가 섞이면 비중이 큰 쪽 prefix를 쓰고, 본문에 나머지를 나열한다.
- 종류가 확연히 갈리고 서로 무관하면 커밋을 나눌 것을 먼저 제안한다.

## 1줄 커밋 메시지 예시

- `post: 개발 블로그 - Cursor IDE 토큰 사용량 절약 가이드 포스팅 추가`
- `post: 여행 블로그 - 토스 체크카드로 태국바트 인출 방법 포스팅 수정`
- `dev: 메인페이지 블로그 소개문구 변경 및 메타 태그 추가`
- `dev: Google Analytics 트래킹 추가`
- `etc: Cursor 용 AI 프롬프트 수정`

## 여러줄 커밋 메시지 예시

```
post: 블로그 포스팅 추가/수정

- 개발 블로그 - Cursor IDE 토큰 사용량 절약 가이드 포스팅 추가
- 여행 블로그 - 토스 체크카드로 태국바트 인출 방법 포스팅 수정
```

## 주의사항

- 사용자 확인 없이 커밋하지 않는다.
- `.env`로 시작하는 파일은 조회하지 않으며, 스테이징 대상에 있으면 커밋 전에 알린다.
- `git add .` 전에 추적되지 않는 파일 목록을 확인해 의도한 파일만 포함시킨다.
- 강제 푸시(`--force`), 히스토리 재작성은 명시적 요청이 없으면 하지 않는다.
